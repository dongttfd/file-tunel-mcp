# FPA-009 - Dynamic Tunnel Health Discovery - Frozen Design

Date: 2026-09-22
Status: FROZEN BEFORE IMPLEMENTATION

## Problem

The default Windows runtime config uses 127.0.0.1:0 for tunnel-client health/admin. Port 0 is resolved by the OS, so FileMCP previously knew only that the tunnel process was running and could not independently probe the real health listener.

The vendored tunnel-client 0.0.12 officially supports --health.url-file and explicitly recommends it with ephemeral health ports.

## Scope

FPA-009 strengthens Windows Observability V1.1 component health. macOS does not currently expose the same component-health dashboard/probe subsystem, so this task does not create an unrelated macOS health UI.

## Selected mechanism

For every Windows LocalMcpRuntime:

1. derive a controlled health URL file path inside the runtime profile directory;
2. delete any stale URL file before every tunnel child launch/restart;
3. pass --health.url-file <path> to tunnel-client run;
4. leave init/doctor behavior unchanged;
5. when configured health address already has a fixed nonzero port, probe it directly as today;
6. when configured address uses port 0, RefreshHealthAsync reads the URL file and resolves the actual endpoint;
7. cache the resolved endpoint only as runtime state, never as user configuration;
8. clear the resolved endpoint on child exit/restart/stop.

## Validation

Resolved URL file input is untrusted runtime output and must be bounded and validated:

- file must exist and be a regular file;
- maximum 512 UTF-8 bytes;
- trim surrounding whitespace;
- absolute URI only;
- scheme must be http;
- no username/password;
- no query or fragment;
- path must be empty or /;
- host must be localhost, 127.0.0.1 or ::1;
- port must be 1..65535.

No URL from the file may cause FileMCP to connect to a LAN/public address.

## Lifecycle

Startup:
validate -> init -> doctor -> build run launch -> clear stale health URL file -> start tunnel child.

Refresh health:
fixed endpoint -> direct probe.
dynamic :0 -> read/validate URL file -> probe resolved endpoint.
missing/invalid URL file -> NotConfigured until a valid file appears.

Unexpected child exit:
- mark existing resolved endpoint unreachable;
- clear cached resolved endpoint;
- next child launch deletes stale file;
- next successful tunnel-client startup rewrites the file;
- next health refresh resolves/probes the new port.

Stop/cleanup:
- clear cached endpoint;
- best-effort delete health URL file.

## Security and privacy

- URL file contains only loopback health base URL, no API key or local auth token.
- file path is generated by FileMCP from already-validated profile state.
- no public health bind is enabled.
- no log parsing is used.
- no secrets are persisted or added to logs.

## Tests

Windows tests must prove:

- strict URL-file parser accepts loopback http URLs and rejects remote hosts, https, credentials, query/fragment, bad ports and oversized content;
- dynamic 127.0.0.1:0 runtime becomes Reachable using fake tunnel-client URL-file output;
- stopping the test listener makes health Unreachable while preserving last success;
- run command contains --health.url-file;
- stale file is deleted before a restarted child launch;
- cleanup deletes the URL file;
- fixed-port health behavior remains unchanged;
- supervisor restart tests remain PASS.
